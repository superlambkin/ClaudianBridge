## 💡 技術的な教訓

### ✅ 良かった点（再現したい）

| # | 教訓 | 適用範囲 |
|---|------|---------|
| 1 | **「Iron Law of 3 strikes」**: 同じ問題で 3 回修正したら、アーキテクチャ自体を見直す（anime-tts ローカル Python → Plachta クラウド API 置換の根拠） | 外部依存の設計 |
| 2 | **マイグレーションは冪等に**: `migratedFrom` / `noticeShown` フラグで「1 度だけ」を担保（chroma / minimax / damarcreative で 3 度同じパターン） | データ移行 |
| 3 | **SSOT 一元化**: バージョン表示を `Plugin.manifest.version` から参照（ハードコード廃止） | 設定・表示 |
| 4 | **統合エントリポイント**: 全 TTS 経路を共通 `speakText` に統一（空テキスト・エラー処理の一元化） | 機能設計 |
| 5 | **読み上げ経路の一元化**: CLI Stop hook 由来の読み上げを廃止しプラグインに一本化（二重読み上げ・ミュート非連動の解消） | システム統合 |
| 6 | **0.x 系の爆速リリース**: 1.0.0 未満は仕様変更自由を活かし、機能追加ごとに minor bump | リリース戦略 |

### ❌ 悪かった点（改善したい）

| # | 教訓 | 影響 | 改善策 |
|---|------|------|------|
| 1 | **Electron renderer の `spawn` 環境相性** | pipe buffer / stdin / stderr の三重苦で不安定 | クラウド API 化（HTTP/SSE）で根本解決 |
| 2 | **読み上げスコープの複雑化** | 📢 検出・ヘッダー/全文・思考ブロック除外が増殖 | 最終回答ゲート + 構造的除外で整理（v0.19.0） |
| 3 | **エンジンごとの暗黙のチャンク上限** | Plachta 1000 字超でエラー・edge は 140 字で非効率 | エンジン別チャンク上限の設定化（v0.18.0） |
| 4 | **複数ターンでの自動読み上げ発火** | 途中ターンの思考を読んでしまう | 最終回答ゲート `detectFinalAnswerState()`（v0.19.0） |
| 5 | **設定 UI の肥大化** | タブ・オプション増加で複雑化 | タブ分割 + 不要設定の削除（minimax / anime-tts） |

## 🧠 プロセス面の教訓

| # | 教訓 | 適用範囲 |
|---|------|---------|
| 1 | **TDD で回帰を防ぐ**: テスト実績 29 → 592 passed へ拡大。各バグ修正時に回帰テストを追加 | 開発プロセス |
| 2 | **実機 UAT と自動テストを併用**: 自動テストでは拾えない DOM 構造依存（realclaudian）は実機で検証 | テスト戦略 |
| 3 | **段階的統合**: 3 プラグイン → 1 プラグインを P2〜P4 で機能単位に分解して統合 | 統合プロジェクト |
| 4 | **worktree で機能並行開発**: chroma-fs / md-save を別 worktree で開発し main へ統合 | チーム開発 |
